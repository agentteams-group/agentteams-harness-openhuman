# Natural Task collaboration

The native Rust Task binding projects prepared evidence through the public Core bridge, retains compact terminal tool output including actual-send facts, and closes a protocol-only phase with an empty visible result. Recovered assignments retain the authenticated Matrix identity. The existing native checkpoint, RunQueue, tool policy and action budget are preserved.

Use the exact Core revision in `versions.env`. Task rules remain in Core: original-conversation intake creates the Task room before planning; normal successful nodes directly notify ready downstream Workers; exceptions and final acceptance notify the Leader. Do not add receiver-specific wakeups, visible ACKs, self-mentions or a second model request for a receipt.

Prepared model context uses `task_context.model_context` / the public `model_context` operation. Terminal model output uses `task_native.model_result` / `model_result`: preserve Task/submission/plan/completion identities, primary receipt and verified extra receipts while omitting repeated canonical snapshots. A queued notification is not an actual send; only the authenticated Core event with `native_id=matrix:$event` supplies the sent fact. No sent fact proves downstream execution.

Native tests and local model/API fixtures are separate from real Matrix multi-Worker end-to-end acceptance. Record source/image versions, tool-call and native-session receipts, model-call counts, exact artifact hashes, remote persistence, Trace visibility and any interventions. Do not describe synthetic fixture success as full Harness admission certification.

Recovered and live inputs both bind the authenticated Matrix actor. A same-owner `completed` Task may settle an existing tool return and persist its actual native history, but never reopen inference or admit new tools. Silent final callbacks still require an authoritative durable result. Successful planning emits no control-receipt chat.

Your native Task and ordinary-message session histories are saved under runtime/openhuman-task-sessions and runtime/openhuman-message-sessions. The Worker sync loop uploads only these owned mutable directories to your private storage prefix; Controller runtime projections and credentials remain excluded. Verify the actual saved history and sent-event facts after a fresh run; a local cache alone does not prove remote durability.

Native Task execution publishes shared Matrix run blocks directly from the engine's ID-bearing call boundary. Keep actual arguments, returned output, timestamps and failure status, including pre-execution rejection; model reasoning is shown only when supplied. Use the native Matrix SDK for structured sends and replacement events, preserving encryption. Progress never enters the native model history and never triggers a sender or recipient turn. Quiet closure closes the existing process fold without an extra chat receipt. Payload previews are bounded and secrets redacted. Standalone adapter fixtures and the full patched-SDK checks are separate evidence layers.

A managed Matrix turn has a 900-second native budget so its five-minute approval window leaves time for actual execution and delivery. The approval gate keeps its existing deadline and ownership checks. Cancellation or timeout closes an already published process as interrupted; it does not report Task success or admit another tool.

Targeted structured native tool decisions reach the existing approval waiter even while unrelated room history is still backfilling. Retain the original event and enforce the configured sender plus the waiter's exact Human, room, request and context binding. Wrong-target or malformed controls and ordinary business messages retain their normal history policy. Consuming a decision never starts a model turn.

Use one display `run_id` for a Worker execution generation: native thinking and tools publish `org.agentteams.run.run_id`, and the saved business reply carries the same `org.agentteams.run_id`. Derive it from the owned room, scope and generation so saved-result delivery can retain it without reading a closed native session. Tool starts and results retain their native `tool_call_id` and edit the same Matrix event. Matrix discussion threads and native model sessions remain separate identities; display metadata never enters model history.

The startup prompt distinguishes ordinary native workspace paths from prepared Task paths. Relative Task file-tool paths already resolve under the current output directory; do not prepend the member's `shared/tasks/` path again. Use a basename there or the exact absolute output path, and use the same absolute path in shell commands. R15 retained the contradictory old-prompt failure rather than counting its misplaced files as a delivery.

Accepted plain messages in an unambiguous active owned Task room are queued for that Task's next native engine boundary. They do not start another ordinary-message Run or emit an acknowledgement. The adapter persists the actual source into Task history and commits its native input receipt before retiring its temporary ordinary-message lease. Approvals, explicit controls, coordination notifications, other rooms and ambiguous concurrent Tasks keep their existing routing; unknown ordinary operations or Task authority failures remain fenced. This routing is covered by the native SDK recovery test with synthetic Controller responses; real Matrix/model acceptance remains a separate gate.

Prepared Task shell commands have a 300-second execution limit so dependency/browser installation is not killed by the ordinary 60-second command budget. Ordinary conversations retain 60 seconds. The original 900-second turn limit, approval deadline, action budget, environment scrubbing and owned process-group cleanup still apply. The patched SDK protocol test checks the real prepared Task scope; the shell regression checks the unchanged ordinary default.

The default outer tool deadline for a prepared Task shell is 310 seconds, leaving time for the inner command deadline and cleanup to return a definitive result. An explicit operator environment override or a different configured deadline remains authoritative. Other tools and ordinary turns retain their existing deadlines.

An owned Task that is waiting for tool verification still owns its unambiguous room supplements, even after its native Run has stopped. Queue those accepted sources for the Task; do not execute new tools or create an ordinary-message Run around the verification fence. Model room history includes business messages and excludes approvals, coordination, controls and progress events. An approval reference is never a Task identity.

If checkpoint or configuration changes invalidate an opaque Task session, retain its original business requirements separately from execution history. Cached source IDs are only ordered locators: read the original bytes from the authenticated Worker's accepted input ledger, verify the same Task room and native persistence, and project each business input once into the fresh session. Never restore old tools, system policy, rendered recovery snapshots or approval/control frames through this path. Saved-result delivery does not load these model inputs, and unknown tool operations still require verification.

## Task-room acceptance

Verify a fresh Task against the [shared Task-room standard](https://github.com/agentscope-ai/AgentTeams/blob/791ac4ccc0a8c3b6d13ef888574dba7b09e1c00f/docs/design/task-room-data-flow-standard.zh-CN.md). Inspect the original Matrix events as well as the Dashboard. The Leader publishes the task overview before the first assignment. Each stage displays its result alongside its collapsed native process and delivers its files before notifying the next Worker. The Leader closes with a readable acceptance report in the task room and returns the report and selected file attachments to the original conversation. Open or download each final file in both rooms and compare its bytes.

The planning wake and retry are authenticated non-chat events. Bind the receipt to its actual Matrix event ID. After a successful submission, persist the downstream delivery fact in the submitting native session only after Matrix confirms the handoff. Replaying delivery must produce one fact, with no public acknowledgement or additional model turn.
